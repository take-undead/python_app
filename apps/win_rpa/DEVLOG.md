# win_rpa 開発の経緯

このアプリを作るまでに決めたこと、途中で判明したこと、まだ終わっていないこと。
仕様と使い方は [README.md](README.md) を見ること。ここは「なぜそうなっているか」と
「今どこにいるか」を残すためのもの。

作成: 2026-08-27 〜 2026-08-28

---

## 1. 何を作ろうとしているか

月 1 回の PC ルーティンワークの自動化。具体的には次の流れ。

1. Windows の業務アプリを起動する
2. 決まった順にボタンを押し、値を入力する
3. アプリに CSV を出力させる
4. 出力された複数の CSV を 1 つに結合する

これをスケジュール実行で無人化することが最終目標。

**対象の業務アプリは開発機（この PC）に入っていない。** そのため、
実機なしで最後まで作れるように練習用のダミーアプリを用意してある。

## 2. 設計で決めたこと

### 記録するのは座標ではなく「要素の同一性」

最初に検討したのはマクロレコーダー方式（マウス座標とキー入力を時系列で記録）
だが、これは採らなかった。ウィンドウ位置が数 px ずれただけで全滅し、
記録された内容を人が読んでも意図が復元できない。月 1 回しか動かさないアプリで
これをやると毎月デバッグすることになる。

代わりに、クリック対象の **AutomationId / 名前 / 種類 / 構造上の位置** を採取して
残し、実行時はそれで要素を探す。照合は 3 段構えで、前段が外れたら次に落ちる。
どの段で見つけたかは実行ログに残す。

### アクションの追加コストを 10 行に抑える

「出来ることが増えると UI が膨らむのでは」という懸念に対する答え。
アクションごとに専用フォームを書くと種類数 × 60 行で増えるが、
入力項目を `logic/actions.py` の `ACTIONS` にデータとして宣言し、
`ui/field_editors.py` が `kind` を見てウィジェットを選ぶ形にした。

結果、アクションを 1 つ増やすコストは宣言 10 行と `runner.py` のハンドラのみ。
**`ui/` は触らない。**

### 制御構造を入れない

`if` / `while` / 変数を入れると手順一覧が入れ子のツリーになり、条件式を書く UI と
デバッグ機能が要る。これはプログラミング言語を作る作業で、規模が桁で変わる。
月次ルーティンは平坦な直線で書けるはずなので、そこは死守する。

特殊処理が必要になったときの逃げ道として `run_python` アクションを 1 つだけ用意した。
用意したスクリプトを呼ぶだけで、ユーザーから見れば普通の操作の 1 つに見える。

### JSON をユーザーに見せない

「JSON が分からないので選択で指定したい」という要望から、方針を変更した。
JSON は内部の保存形式に徹し、画面には一切出さない。
要素はピッカー、アプリはショートカット一覧、ウィンドウ題名は開いている
ウィンドウの一覧、差し込み変数は「差し込み ▼」メニューから選ぶ。

自由入力が残っているのは、入力値そのもの（対象アプリに打ち込む文字列）だけ。

### 全自動レコーダーは作らない

バックグラウンドで全操作をフックする方式は、実装量が跳ね上がる割に余計な
クリックまで拾って結局手で削ることになる。半自動のピッカー
（マウスを乗せて F8）にして、**手順の骨格は人が組み、識別子の採取だけ機械にやらせる**
分担にした。要素の種類から操作も自動推定する（Button → 押す、Edit → 文字入力）。

### スケジューラを自作しない

月 1 回のために常駐プロセスを持たない。Windows タスクスケジューラに
`schtasks` で登録する。PC 再起動やログオン後の復帰は OS に任せる。

### 用語は「シナリオ」と「手順」で確定（2026-08-28）

「今時で言えば、手順との表記はワークフロー？」と聞かれ、検討したうえで
**変えないと決めた**。同じ問いが再燃しないよう理由を残す。

まず対応がずれている。今どきのツールはどれも 2 階層で、この app と同じ構造。
**ワークフローに当たるのは「手順」ではなく「シナリオ」のほう**。

| ツール | 全体（＝シナリオ） | 1 つ 1 つ（＝手順） |
| --- | --- | --- |
| GitHub Actions | workflow | **step** |
| Zapier | Zap | **step** |
| Power Automate | フロー | アクション |
| n8n | workflow | node |
| UiPath | ワークフロー | アクティビティ |

「手順」は step の直訳なので、今どきの表記としてもそのまま。
改名の候補になるのはシナリオ → ワークフローだが、これは採らない。

1. **日本の業務 RPA では「シナリオ」が標準語。** WinActor がこれをシナリオと
   呼んでいる。対象ユーザーが RPA に触れたことがあるならこちらが通じる
2. **「ワークフロー」は承認ワークフローと紛らわしい。** 日本の業務現場では
   申請・承認の回覧のことだと受け取られる率がそこそこある

なお画面の文字列とコード上の名前は分けてある（`Step` / `Scenario` / JSON の
`steps`）。表示だけ変えたくなった場合、保存形式は触らずに済む。

## 3. 途中で判明した技術的な事実

詳細は [README.md](README.md) の「分かっていること」に書いた。ここでは
どういう順で分かったかを残す。

| # | 事実 | どう表面化したか |
| --- | --- | --- |
| 1 | Tkinter のウィジェットは UIA から見えない | 雛形アプリを UIA で覗いたら名前のない `Pane` の入れ子だった。**ダミーアプリを WinForms で作り直す判断につながった** |
| 2 | PowerShell 5.1 は BOM なし UTF-8 の .ps1 を ANSI で読む | ダミーアプリが構文エラーで起動しなかった。`-EncodedCommand` で回避 |
| 3 | WinForms の `class_name` は実行ごとに変わるハッシュを含む | 照合に使わない設計にした |
| 4 | OneDrive 環境でデスクトップの実体が移動する | この開発機がその状態だった |
| 5 | `Application.start()` の `WaitForInputIdle` はコンソール起動の exe で落ちる | ランチャー型アプリで再現。`wait_for_idle=False` に |
| 6 | 起動用 exe と画面を持つプロセスが別なことがある | `close_app` がランチャーだけ殺していた。PID の結び直しを追加 |
| 7 | 共通ダイアログ（`#32770`）は UIA の走査から漏れる | 保存ダイアログが 30 秒待っても見つからなかった。Win32 では `visible=True` で存在していた。`logic/winfind.py` を追加 |
| 8 | 共通ダイアログのボタン名は日本語 Windows でも `Save` / `Cancel` | 「保存」で探して見つからなかった。`auto_id`（IDOK=1）で照合 |
| 9 | ファイル名欄への UIA `SetValue` は COM エラーで失敗する | 入力方法を 5 通り比較し、win32 の `WM_SETTEXT` だけが成功 |
| 10 | ファイル名欄の `control_id` は Windows 11 で 1001 | よく知られた 1148 は UIA 側に要素すら無かった |
| 11 | `schtasks` の出力は UTF-8（cp932 ではない） | 登録は成功するのに一覧に出なかった。タスク名が化けていた |
| 12 | Tk のウィジェットに `_register` という名前を付けると壊れる | スケジュール画面が生成された瞬間に落ちて何も表示されなかった |
| 13 | `pywinauto` を import するとプロセスが MTA になり、`askdirectory` が固まる | 「フォルダを作る」の［参照...］を押すと**ダイアログが出ないまま固まった**。`pywinauto` が `sys.coinit_flags = 0` を設定しており、シェルのフォルダ選択は STA 必須。**ファイル選択（comdlg32）は影響を受けない**ので、既存の［参照...］では表面化していなかった |

7〜10 は保存ダイアログ 1 つを動かすために全部必要だった。**業務アプリは
この共通ダイアログを多用するので、ここが通らないと実用にならない。**

13 は「ファイル選択は動くのにフォルダ選択だけ固まる」という形で出た。
原因が自分のコードではなく **import しているライブラリの副作用**だったので、
切り分けは「pywinauto を import する／しない」×「askdirectory ／
askopenfilename」の 4 通りを別プロセスで走らせ、**窓が出たかどうか**を
外から数える形にした（固まる不具合は、中から assert しても取れない）。

## 4. ユーザーからの指摘で直したこと

作ったあとで使ってもらい、次を直した。いずれも「自分では気づけなかった」類の指摘。

| 指摘 | 実際に起きていたこと |
| --- | --- |
| ウィンドウ題名が手入力なのが不便 | 自由入力が 1 か所だけ残っていた。開いているウィンドウの一覧から選ぶ形に変更（UWP の隠しウィンドウは `DWMWA_CLOAKED` で除外） |
| シナリオは 1 つしか持てないのか | 複数持てるが、切り替えで未保存の編集が黙って消える／同名で上書きされる／使えない文字を含む別名が同じファイルになる、の 3 つのバグがあった |
| スケジュール画面に何も表示されない | 事実 #12 と #11。画面がそもそも開けていなかった |
| スケジュールの一覧表示と削除は不要か | 必要だった。**シナリオを削除してもタスクが残り、毎月起動しては失敗し続ける状態**だった |
| ［＋ 手順を追加］が見つけにくい | `ttk.Menubutton` は Windows のテーマで枠が描かれずラベルに見える。一覧の右上に移し、`ttk.Button` ＋ 専用スタイルに変更 |
| 手順をツリーにしてほしい／ファイル操作が要る | 下の「5. 手順のグループとファイル操作」に分けて書いた |
| 今作られたグループはどういう意味？ | **ツリーにする対象を取り違えていた。** 求められていたのは［＋ 手順を追加］の分類。5 章に書いた |
| CSV をまとめるを特殊動作に | 汎用の結合をやめ、作ったフォルダに縛って日時順に並べる形へ。前提が無ければ手順に入れられないようにした。5 章に書いた |
| 用途は「日次ファイルを 1 か月ぶん連続データにする」 | **時刻を捨てていた。** 同じ日の中が元ファイルの並び順のまま残る実装だった。時刻まで読むよう直し、まとまった期間をログに出すようにした |

| バーにヘルプや、バージョン、作成者は要らない？ | **版は要る**（exe を別 PC にコピーして月 1 回動かすため、どのビルドか分からないと調査できない）。作成者は不要、メニューバーはツールバーと二重になるので作らない。ツールバー右端の版表示＋クリックで「について」の小窓にした |

## 5. 手順のグループとファイル操作（2026-08-28 追加）

### 何を求められたか

「手順をツリーにして、ファイル操作を追加して、フォルダ選択やフォルダ作成が
出来るようにして、フォルダ名も年月日のように自動設定パターンで作るような
項目が欲しい」。

追加で「**ファイルを消す行為は危険なので入れない**」。

### ツリーにするが、入れ子は作らない

「ツリー」で最初に浮かぶのは `if` / 繰り返しを持つ入れ子だが、2 章で
入れないと決めている。何が欲しいのかを確認したところ、**長くなった手順を
読めるように束ねたい**（分岐は要らない）だった。

そこで `Step.group` という**名札を 1 つ足すだけ**にした。

- `Scenario.steps` は今まで通り 1 本のリスト。実行順も保存形式も変わらない
- 同じ名札が隣り合っている区間を `Scenario.groups()` が塊として返す
- 画面（`ttk.Treeview`）がそれを親ノードとして描く

入れ物のクラスを作らなかったのは、作った瞬間に `Runner` と `upto`
（ここまで試し実行）に「入れ子の何番目まで」という概念が要るようになり、
分岐を入れないと決めた意味が薄れるため。名札方式なら `runner.py` は 1 行も
変わらない。

副作用として、同じ名札が離れて置かれると見出しが 2 つに割れる。
グループ操作の直後だけ `normalize_groups()` で先に出たほうへ寄せている。
↑↓ の入れ替えでは呼ばない（並べ替えた結果が勝手に動くと何が起きたか
分からなくなる）。

グループの境目で ↑↓ を押したときは、**入れ替えずにまず名札だけ変える**。
1 回で両方やると、境目にいる手順を隣のグループへ移す操作が無くなる。

### 「グループ」を取り違えた

上の束ねる機能を作ったあとで「今作られたグループはどういう意味？」と聞かれた。
**求められていたのは［＋ 手順を追加］のメニューの分類**だった。
「手順の種類が増えそうなので」＝操作の種類が 14 個も平らに並んでいて探せない、
という話で、シナリオ内の手順を束ねる話ではなかった。

分類は `ActionSpec.category` として**宣言側に持たせた**。画面は
`actions_by_category()` が返したものを入れ子メニューに組むだけなので、
操作を増やしても `ui/` は触らないという 2 章の約束を守れている。
`ui/step_form.py` の「種類」ドロップダウンも同じ並びにした
（入れ子にできないぶん、せめて探す場所を一致させるため）。

手順のグループのほうは残してある。どちらも「増えたものを読めるようにする」
機能で、効く場面が違う（片方は操作の一覧、片方は組み上がったシナリオ）。

### 「CSV をまとめる」を特殊な手順にした

もとは「まとめる対象のパターン」と「出力先」を指定させる汎用の結合だった。
これを**前の手順が作ったフォルダに縛る**形に変えた。

- 対象は `Runner._created_folder`（「フォルダを作る」で最後に作った場所）の CSV 全部
- 結果は同じフォルダに置く
- 見出しの先頭付近にある日時の列で古い順に並べ替える
- 分類も「ファイルとフォルダ」から「その他」へ移した

想定している使い方は次のとおり（あとから聞いた）。

```
日次/  ← 対象アプリが毎日 1 本ずつ吐く
    売上_20260801.csv        1  フォルダを作る        → 日次/202608
    ...                      2  ファイルをコピーする  → 31 本を入れる
    売上_20260831.csv        3  CSV をまとめる        → 月次_202608.csv
```

対象を選ばせないのは、まとめる先が「作ったフォルダ」だと決まっている以上、
そこに入っているものが対象という以外の解釈が無いため。設定項目を 1 つ
減らせるうえ、パターンを打ち間違えて 0 件になる事故も消える。

`_created_folder` を `_work_dir` と別に持っているのは、「作ったフォルダを
以降の保存先にする」を外していても、まとめる先は作った場所だから。

**出力ファイルを対象から除いている。** 除かないと 2 回目に動かしたとき
前回の結果を自分に取り込んで行が倍になる。前の実装でも起きうる問題だった。

### 日時の列は自動で見つける

「データの先頭付近にある日付」で並べる、という要件をそのまま実装した。
列名を打たせない（2 章）ので、**見出しの先頭 4 列**から探す。

1. 名前に「日時」「日付」「年月日」「date」などが入っている列を先に試す
2. 駄目なら、その列の値を実際に日時として読めるか見る（先頭 50 行の 8 割）

ファイルごとに書き方が違っても混ぜて並べられる（`2026/8/5` と `20260810` と
`2026年8月1日` が同じ列に混在していても正しく並ぶことを確認した）。
読めなかった行は**捨てずに末尾**へ回す。日時列が見つからなければ、
失敗させず読み込み順のままにして警告を出す（並んでいないだけで使えるため）。

### 時刻を落としていた（用途を聞いて直した）

最初の実装は日付だけを見ていた。`2026-08-28 10:30:00` を空白で切って
`2026-08-28` として読み、**時刻を捨てていた**。

そのあとに用途を聞いた。「1 日 1 本の CSV が貯まるので、1 か月ぶんを
フォルダに入れて 1 本の連続データにしたい。データには日時が記録されている」。

この用途では時刻を落とすと、**同じ日の中が元ファイルの並び順のまま残る**。
1 日 1 ファイルなら日ごとの順序は合うので一見動いて見えるが、1 つのファイルに
複数日が混ざったり、ファイル内が時刻順でなかった時点で崩れる。
「連続データにする」という目的からすると、静かに間違った結果を出す実装だった。

日時の書式（時刻付き 15 種）を先に試し、駄目なら日付だけの書式に落とす形に
変えた。`T` 区切り（ISO）とミリ秒も通る。**空白で切る処理は最後の保険**に
下げてある（後ろに余計な文字が付く出力のため）。

あわせて、まとまった**期間を実行ログに出す**ようにした。

```
[info]   2026-08-01 10:00:00 〜 2026-08-31 17:00:00 の 93 行
```

月 1 回・無人で動くものなので、1 か月ぶんが揃っているかをファイルを開かずに
確かめられる形が要る。日数が足りていなければここで気づける。

### 前提のある手順は、置く前に止める

「フォルダ作成工程が無ければ手順に入れられない様に」という要件。
前提を `ActionSpec.requires` として宣言側に持たせ、3 か所で効かせた。

| どこ | 何をするか |
| --- | --- |
| ［＋ 手順を追加］ | 満たしていない操作を灰色にし、理由をラベルに出す |
| 一覧・保存前の検証 | `Scenario.step_problems()` が ⚠ を付ける |
| 実行の開始時 | **対象アプリを起動する前に**止める |

メニューで止めるだけでは足りない。「種類」のドロップダウンで既存の手順を
後から「CSV をまとめる」に切り替えられるし、`--run` の無人実行は
画面を通らない。実行時の判定を `run()` の先頭に置いたのは、8 手順進んでから
「先にフォルダを作る手順が要る」と言われても遅いため。

判定を `Step.validate()` ではなく `Scenario.step_problems()` に置いたのは、
Step が自分の位置を知らないから（「**前に**あるか」を見る必要がある）。

### まだベータであることを画面に出す

「バーにヘルプや、バージョン、作成者は要らない？」という問いから。
3 つを分けて考え、**版だけ入れた**。

| | 判断 | 理由 |
| --- | --- | --- |
| バージョン | 入れる | exe を対象 PC にコピーして月 1 回動かす。1 か月後に「動いていない」となったとき、向こうに載っているのがどのビルドか分からないと調査が始まらない |
| 作成者 | 入れない | 社内の 1 人用ツールで、増える情報が無い |
| ヘルプ（メニュー） | 入れない | ファイル/編集/ヘルプ を足すとツールバーの［新規］［保存］［削除］と二重になる |

置き場所はツールバーの右端。メニューバーを新設せずに済み、
**⚠ ベータ版 0.9.0** と出しておけば「まだ作成中」が一目で分かる。
押すと用途と注意点の小窓が開く形にした。

文言は `logic/appinfo.py` に集めてある（画面と、将来ログや exe の
情報から使うときに食い違わないようにするため）。`IS_BETA` を False に
すると色と警告が消える。実機確認が済んだときの 1 行変更で済ませたい。

**実行ログと exe のプロパティにはまだ入れていない。** 無人実行の調査は
`logs/*.log` を読むので、本当はそこに版が入っているのが一番効く。
8 章の積み残しに書いた。

### 保存先を実行中に動かせるようにした

`Runner._work_dir` は今まで実行中ずっと固定だった。「フォルダを作る」
「保存先フォルダを選ぶ」で差し替えられるようにし、`{work_dir}` の
差し込み変数も同時に更新している。片方だけ変えると、相対パスの解決結果と
`{work_dir}` を書いた文字列が食い違う。

確認実行では**フォルダは作らないが、切り替えだけは行う**。切り替えないと
確認実行のときだけ以降のパスが本番と違うものになり、確認の意味が消える。

### フォルダ名は打たせない

`{yyyymm}` を覚えさせない方針（2 章）をフォルダ名にも通した。
［型 ▼］に年月日の並べ方を用意し、選ぶと欄が丸ごと置き換わる。
差し込みのような「追記」にしなかったのは、フォルダ名は丸ごと決まることが
ほとんどで、継ぎ足すと打ち間違いの余地が残るため。

選んだ結果**出来上がるフルパスをその場に出す**。毎月同じフォルダに
上書きしていないかを、実行する前に目で確かめられる。

同じ考えで、コピー対象の選び方（`file_pattern`）は［型 ▼］から
「すべて」「CSV すべて」などを選ばせ、**今そこに何件あるか**を出す。
0 件のまま気づかず組んでしまうのを防ぐため。

### 消す操作は入れない

削除アクションは作らなかった。月 1 回・無人で動くものが誤って消すと、
気づくのが 1 か月後になる。

コピーの「同じ名前のとき」の既定も**飛ばす**にした。毎月動かすので
行き先に前月分が残っていても止まらず、かつ黙って消さない。上書きは
選んだときだけ（そのときだけ行き先のファイルが消える）。

### 判明したこと

`Path.glob()` は絶対パスを渡すと `NotImplementedError` を投げる
（`OSError` でも `ValueError` でもない）。ファイルの選び方の欄に
フルパスを貼られると、画面のプレビューと実行の両方で捕まえ損ねて
「想定外のエラー」になる。両方で明示的に受けている。

`tk.Menu.post()` は Windows で**そこから戻ってこない**（メニューを閉じるまで
Tk 内部のモーダルループに入る）。検証スクリプトでメニューを開いた状態を
撮ろうとしてハングした。メニューの中身は `index()` / `type()` /
`entrycget()` / `invoke()` で開かずに確かめられるので、そちらで見ること。

## 6. 今どこまで来ているか

### 動作を確認したもの

すべてダミーアプリ（`tools/mock_target.py`）相手。

- **通し実行** — 起動 → 年月入力 → 区分選択 → チェック → 集計 → CSV 出力 →
  保存ダイアログ → 行数検証 → 終了（アクションを増やす**前**に取ったもの。
  下の「まだ確認していないもの」4 を参照）
- **確認実行（dry-run）** — 9 手順すべて、操作せず要素の存在だけ確認
- **途中まで実行（`upto`）** — 指定した手順で停止
- **無人実行（`--run`）** — スケジューラから呼ばれる経路。ログがファイルに残る。
  差し込み変数 `{prev_yyyy-mm}` が前月に展開されることも確認
- **UI** — 14 アクションすべてが正しい項目でフォームを組む。完了条件の動的切り替え、
  種類変更時の項目引き継ぎ、未入力での実行阻止、並べ替え・複製・削除
- **ダイアログ 4 種** — スケジュール／アプリ選択／要素ピッカー／グループ選択の生成
- **ファイル操作** — フォルダ作成（差し込み展開・使えない文字の検出）、保存先の
  切り替え、コピー／移動（連番付きの改名・同名を飛ばす）、2 回続けて動かしても
  壊れないこと、確認実行でファイルを作らないこと
- **グループ** — 束ねる・飛び飛びの選択を寄せる・改名・折りたたみ・グループごとの
  移動・境目での移動・保存と読み直し
- **CSV をまとめる** — 日時の書き方 15 種の読み取り（時刻・ISO・ミリ秒つき）、
  列の自動判定（名前／中身／先頭から離れた列は使わない）、書き方が混ざった

- **前提条件** — メニューで灰色になる／理由がラベルに出る／直接呼んでも入らない／
  挿入位置より後ろの手順は数えない／実行が手順 1 で止まる
- **シナリオ管理** — 複数保存・切り替え・未保存時の引き止め・名前衝突の検出
- **スケジュール** — 登録・一覧・個別削除・シナリオ削除／改名への追従
- **ショートカット起動** — `os.startfile` で `.lnk` から起動し、閉じて残らないこと

## 7. 検証のやり方

CLAUDE.md の方針どおり、検証スクリプトはリポジトリに置かず一時フォルダに書いて捨てている。
書き直すときの中身を残しておく。共通の下ごしらえは次の 2 つ。

- `sys.path.insert(0, "apps/win_rpa")` してから `logic` / `ui` を import する
- `messagebox` を差し替えて、ダイアログでスクリプトが止まらないようにする

```python
import ui.main_window as mw
errors: list[str] = []
mw.messagebox.showerror = lambda t, m, **k: errors.append(f"{t}: {m}")
mw.messagebox.askyesno = lambda t, m, **k: True
```

| 検証 | 内容 |
| --- | --- |
| ピッカー | ダミーを起動し、各ウィジェットの座標から `capture_at()`。`auto_id` / 種類 / 推定操作 / JSON 往復を確認 |
| 通し実行 | 採取した要素で `Scenario` を組み、`Runner` で dry-run と本実行。2 か月分まわして結合まで |
| 無人実行 | `subprocess` で `main.py --run <名前>` を叩き、CSV とログファイルを確認。存在しない名前で終了コード 2 |
| UI | `root.update()` を回し、全アクションのフォーム項目・完了条件の切り替え・並べ替えを確認 |
| グループ | `Treeview` の iid（`g<番号>` / `s<位置>`）を直接 `selection_set` して各操作を叩き、`Step.group` の並びを見る |
| ファイル操作 | 一時フォルダに CSV を置き、`Runner` を通してから実際に出来たファイルを数える |
| まとめる | 日時の書き方を混ぜた CSV を 3 本置き、まとめた結果の列を読んで**並び順そのもの**を確かめる。2 回続けて動かして行が倍にならないことも見る |
| 1 か月ぶん | **実際の使い方どおりに組む。** 1 日 3 行 × 31 日の日次ファイルを作り（各日は時刻をわざとばらす）、フォルダ作成 → コピー → まとめを通して、結果が時刻まで単調に並ぶことと前月分が混ざらないことを見る |
| 前提条件 | メニュー項目の `state` と `label`、`Scenario.validate()`、`Runner.run()` の 3 か所で止まることを別々に確かめる |
| 追加メニュー | `post()` せずに `index("end")` / `type(i)` / `entrycget(i, "label")` で中身を読む。**全アクションに辿り着けること**を集合の比較で確かめる（分類の付け忘れが一番起きやすい） |
| ダイアログ | 4 つの `Toplevel` を 1 回ずつ生成し `winfo_exists()` を見る。**生成時に落ちるバグがあったので必須** |
| シナリオ管理 | 3 本作って切り替え、未保存時の引き止め、名前衝突 |
| スケジュール | 実際に `schtasks` へ登録 → 一覧 → 個別削除 → シナリオ削除で追従。**後始末を必ず入れる** |

### 注意

- 失敗するとダミーアプリのウィンドウが残る。開始時と各実行後に
  `MainWindowTitle` が空でない `powershell` プロセスを落とすこと。
  残ったまま次を動かすと `ElementAmbiguousError` になる。
- PowerShell から Python を叩くとき `2>$null` を付けない。
  Windows PowerShell 5.1 はネイティブコマンドの stderr をリダイレクトすると
  終了コードを壊し、成功しているのに失敗に見える。
- Tkinter の画面確認は `Desktop(backend="win32")` で `capture_as_image()` すると
  画像で確かめられる（UIA では中身が見えないため）。

## 8. 積み残しの改善案

急ぎではないが、使っていて不便なら。

- **手順のコピーを別シナリオへ** — 似た手順を作るときに毎回組み直している
- **実行ログを画面から開く** — 今は `logs/` を手で開く必要がある
- **失敗した手順から再開** — 途中で落ちたとき、最初からやり直している
- **要素の再取得** — アプリ更新で見つからなくなった要素を、エラー画面から直接
  選び直せるようにする（今は手順を選び直して［要素を選ぶ...］を押す）
- **並べ替えの列を人が選べる逃げ道** — 今は先頭 4 列から自動で見つける。
  日時の列が 5 列目以降にある出力に当たったら、そのときに考える
  （先に付けると、まず自動判定を疑う手間が増えるだけなので入れていない）
- **まとめる前の重複チェック** — 同じ日のファイルを二重に入れると行が重複する。
  今は「同じ名前のとき＝飛ばす」で名前が同じなら防げるが、名前違いの
  同一データは通る
- **手順のドラッグ移動** — グループ間の移動は今 ↑↓ の押し直しでやっている
- **実行ログの先頭に版を出す** — 無人実行の失敗は `logs/*.log` を見て調べる。
  「いつのコードのログか」が分からないと突き合わせられない
- **exe のプロパティに版を入れる** — 右クリック → プロパティ → 詳細が今は空。
  Windows で人が最初に見る場所なので入れておきたい（PyInstaller の
  `--version-file`。`tools/build.py` に口を足す必要がある）
- **ビルドから numpy を外す** — 配布フォルダ 63.5 MB のうち 26.7 MB が numpy で、
  win_rpa は実行時に import していない（`requirements.txt` が全アプリ共有で、
  webcam / esp32cam の OpenCV 用に入っているものを PyInstaller が拾っている）
