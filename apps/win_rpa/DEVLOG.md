# win_rpa 開発の経緯

このアプリを作るまでに決めたこと、途中で判明したこと、まだ終わっていないこと。
仕様と使い方は [README.md](README.md) を見ること。ここは「なぜそうなっているか」と
「今どこにいるか」を残すためのもの。

作成: 2026-08-27 〜 2026-08-28

---

## 1. 何を作ろうとしているか

月 1 回の PC ルーティンワークの自動化。具体的には次の流れ。

1. Windows の業務アプリを起動する
2. 決まった順にボタンを押し、値を入力する
3. アプリに CSV を出力させる
4. 出力された複数の CSV を 1 つに結合する

これをスケジュール実行で無人化することが最終目標。

**ただし月次に限る作りにはなっていない。** 作業のまとまりは「シナリオ」
として何本でも持て、一覧から選んでそのとき 1 本だけ動かせる。
スケジュール登録は、そのうちの 1 つの使い方でしかない（14 章）。

**対象の業務アプリは開発機（この PC）に入っていない。** そのため、
実機なしで最後まで作れるように練習用のダミーアプリを用意してある。

## 2. 設計で決めたこと

### 記録するのは座標ではなく「要素の同一性」

最初に検討したのはマクロレコーダー方式（マウス座標とキー入力を時系列で記録）
だが、これは採らなかった。ウィンドウ位置が数 px ずれただけで全滅し、
記録された内容を人が読んでも意図が復元できない。月 1 回しか動かさないアプリで
これをやると毎月デバッグすることになる。

代わりに、クリック対象の **AutomationId / 名前 / 種類 / 構造上の位置** を採取して
残し、実行時はそれで要素を探す。照合は 3 段構えで、前段が外れたら次に落ちる。
どの段で見つけたかは実行ログに残す。

### アクションの追加コストを 10 行に抑える

「出来ることが増えると UI が膨らむのでは」という懸念に対する答え。
アクションごとに専用フォームを書くと種類数 × 60 行で増えるが、
入力項目を `logic/actions.py` の `ACTIONS` にデータとして宣言し、
`ui/field_editors.py` が `kind` を見てウィジェットを選ぶ形にした。

結果、アクションを 1 つ増やすコストは宣言 10 行と `runner.py` のハンドラのみ。
**`ui/` は触らない。**

### 制御構造を入れない

`if` / `while` / 変数を入れると手順一覧が入れ子のツリーになり、条件式を書く UI と
デバッグ機能が要る。これはプログラミング言語を作る作業で、規模が桁で変わる。
月次ルーティンは平坦な直線で書けるはずなので、そこは死守する。

特殊処理が必要になったときの逃げ道として `run_python` アクションを 1 つだけ用意した。
用意したスクリプトを呼ぶだけで、ユーザーから見れば普通の操作の 1 つに見える。

### JSON をユーザーに見せない

「JSON が分からないので選択で指定したい」という要望から、方針を変更した。
JSON は内部の保存形式に徹し、画面には一切出さない。
要素はピッカー、アプリはショートカット一覧、ウィンドウ題名は開いている
ウィンドウの一覧、差し込み変数は「差し込み ▼」メニューから選ぶ。

自由入力が残っているのは、入力値そのもの（対象アプリに打ち込む文字列）だけ。

### 全自動レコーダーは作らない

バックグラウンドで全操作をフックする方式は、実装量が跳ね上がる割に余計な
クリックまで拾って結局手で削ることになる。半自動のピッカー
（マウスを乗せて F8）にして、**手順の骨格は人が組み、識別子の採取だけ機械にやらせる**
分担にした。要素の種類から操作も自動推定する（Button → 押す、Edit → 文字入力）。

### スケジューラを自作しない

月 1 回のために常駐プロセスを持たない。Windows タスクスケジューラに
`schtasks` で登録する。PC 再起動やログオン後の復帰は OS に任せる。

### 用語は「シナリオ」と「手順」で確定（2026-08-28）

「今時で言えば、手順との表記はワークフロー？」と聞かれ、検討したうえで
**変えないと決めた**。同じ問いが再燃しないよう理由を残す。

まず対応がずれている。今どきのツールはどれも 2 階層で、この app と同じ構造。
**ワークフローに当たるのは「手順」ではなく「シナリオ」のほう**。

| ツール | 全体（＝シナリオ） | 1 つ 1 つ（＝手順） |
| --- | --- | --- |
| GitHub Actions | workflow | **step** |
| Zapier | Zap | **step** |
| Power Automate | フロー | アクション |
| n8n | workflow | node |
| UiPath | ワークフロー | アクティビティ |

「手順」は step の直訳なので、今どきの表記としてもそのまま。
改名の候補になるのはシナリオ → ワークフローだが、これは採らない。

1. **日本の業務 RPA では「シナリオ」が標準語。** WinActor がこれをシナリオと
   呼んでいる。対象ユーザーが RPA に触れたことがあるならこちらが通じる
2. **「ワークフロー」は承認ワークフローと紛らわしい。** 日本の業務現場では
   申請・承認の回覧のことだと受け取られる率がそこそこある

なお画面の文字列とコード上の名前は分けてある（`Step` / `Scenario` / JSON の
`steps`）。表示だけ変えたくなった場合、保存形式は触らずに済む。

## 3. 途中で判明した技術的な事実

詳細は [README.md](README.md) の「分かっていること」に書いた。ここでは
どういう順で分かったかを残す。

| # | 事実 | どう表面化したか |
| --- | --- | --- |
| 1 | Tkinter のウィジェットは UIA から見えない | 雛形アプリを UIA で覗いたら名前のない `Pane` の入れ子だった。**ダミーアプリを WinForms で作り直す判断につながった** |
| 2 | PowerShell 5.1 は BOM なし UTF-8 の .ps1 を ANSI で読む | ダミーアプリが構文エラーで起動しなかった。`-EncodedCommand` で回避 |
| 3 | WinForms の `class_name` は実行ごとに変わるハッシュを含む | 照合に使わない設計にした |
| 4 | OneDrive 環境でデスクトップの実体が移動する | この開発機がその状態だった |
| 5 | `Application.start()` の `WaitForInputIdle` はコンソール起動の exe で落ちる | ランチャー型アプリで再現。`wait_for_idle=False` に |
| 6 | 起動用 exe と画面を持つプロセスが別なことがある | `close_app` がランチャーだけ殺していた。PID の結び直しを追加 |
| 7 | 共通ダイアログ（`#32770`）は UIA の走査から漏れる | 保存ダイアログが 30 秒待っても見つからなかった。Win32 では `visible=True` で存在していた。`logic/winfind.py` を追加 |
| 8 | 共通ダイアログのボタン名は日本語 Windows でも `Save` / `Cancel` | 「保存」で探して見つからなかった。`auto_id`（IDOK=1）で照合 |
| 9 | ファイル名欄への UIA `SetValue` は COM エラーで失敗する | 入力方法を 5 通り比較し、win32 の `WM_SETTEXT` だけが成功 |
| 10 | ファイル名欄の `control_id` は Windows 11 で 1001 | よく知られた 1148 は UIA 側に要素すら無かった |
| 11 | `schtasks` の出力は UTF-8（cp932 ではない） | 登録は成功するのに一覧に出なかった。タスク名が化けていた |
| 12 | Tk のウィジェットに `_register` という名前を付けると壊れる | スケジュール画面が生成された瞬間に落ちて何も表示されなかった |
| 13 | `pywinauto` を import するとプロセスが MTA になり、`askdirectory` が固まる | 「フォルダを作る」の［参照...］を押すと**ダイアログが出ないまま固まった**。`pywinauto` が `sys.coinit_flags = 0` を設定しており、シェルのフォルダ選択は STA 必須。**ファイル選択（comdlg32）は影響を受けない**ので、既存の［参照...］では表面化していなかった |
| 14 | 対象アプリの起動用ファイルが `.kww`（固有拡張子）だった | 「起動できないファイルが有る」。CreateProcess は関連付けもショートカットも解決しない。6 章に書いた |
| 15 | `WScript.Shell.CreateShortcut` は `.lnk` / `.url` 以外を COM エラーで拒否する | 拡張子を変えたシェルリンクを読ませて確認。`IShellLink` + `IPersistFile` なら拡張子を問わず読めた |
| 16 | `win32timezone` は PyInstaller の解析に出ないので同梱されない | **exe でだけ**ショートカットの解決が `ModuleNotFoundError` で落ちた。pywin32 が COM の日時変換で遅延 import している。`tools/build.py` に `--hidden-import` を足した |

7〜10 は保存ダイアログ 1 つを動かすために全部必要だった。**業務アプリは
この共通ダイアログを多用するので、ここが通らないと実用にならない。**

13 は「ファイル選択は動くのにフォルダ選択だけ固まる」という形で出た。
原因が自分のコードではなく **import しているライブラリの副作用**だったので、
切り分けは「pywinauto を import する／しない」×「askdirectory ／
askopenfilename」の 4 通りを別プロセスで走らせ、**窓が出たかどうか**を
外から数える形にした（固まる不具合は、中から assert しても取れない）。

## 5. 手順のグループとファイル操作（2026-08-28 追加）

### 何を求められたか

「手順をツリーにして、ファイル操作を追加して、フォルダ選択やフォルダ作成が
出来るようにして、フォルダ名も年月日のように自動設定パターンで作るような
項目が欲しい」。

追加で「**ファイルを消す行為は危険なので入れない**」。

### ツリーにするが、入れ子は作らない

「ツリー」で最初に浮かぶのは `if` / 繰り返しを持つ入れ子だが、2 章で
入れないと決めている。何が欲しいのかを確認したところ、**長くなった手順を
読めるように束ねたい**（分岐は要らない）だった。

そこで `Step.group` という**名札を 1 つ足すだけ**にした。

- `Scenario.steps` は今まで通り 1 本のリスト。実行順も保存形式も変わらない
- 同じ名札が隣り合っている区間を `Scenario.groups()` が塊として返す
- 画面（`ttk.Treeview`）がそれを親ノードとして描く

入れ物のクラスを作らなかったのは、作った瞬間に `Runner` と `upto`
（ここまで動かす）に「入れ子の何番目まで」という概念が要るようになり、
分岐を入れないと決めた意味が薄れるため。名札方式なら `runner.py` は 1 行も
変わらない。

副作用として、同じ名札が離れて置かれると見出しが 2 つに割れる。
グループ操作の直後だけ `normalize_groups()` で先に出たほうへ寄せている。
↑↓ の入れ替えでは呼ばない（並べ替えた結果が勝手に動くと何が起きたか
分からなくなる）。

グループの境目で ↑↓ を押したときは、**入れ替えずにまず名札だけ変える**。
1 回で両方やると、境目にいる手順を隣のグループへ移す操作が無くなる。

### 「グループ」を取り違えた

上の束ねる機能を作ったあとで「今作られたグループはどういう意味？」と聞かれた。
**求められていたのは［＋ 手順を追加］のメニューの分類**だった。
「手順の種類が増えそうなので」＝操作の種類が 14 個も平らに並んでいて探せない、
という話で、シナリオ内の手順を束ねる話ではなかった。

分類は `ActionSpec.category` として**宣言側に持たせた**。画面は
`actions_by_category()` が返したものを入れ子メニューに組むだけなので、
操作を増やしても `ui/` は触らないという 2 章の約束を守れている。
`ui/step_form.py` の「種類」ドロップダウンも同じ並びにした
（入れ子にできないぶん、せめて探す場所を一致させるため）。

手順のグループのほうは残してある。どちらも「増えたものを読めるようにする」
機能で、効く場面が違う（片方は操作の一覧、片方は組み上がったシナリオ）。

### 「CSV をまとめる」を特殊な手順にした

もとは「まとめる対象のパターン」と「出力先」を指定させる汎用の結合だった。
これを**前の手順が作ったフォルダに縛る**形に変えた。

- 対象は `Runner._created_folder`（「フォルダを作る」で最後に作った場所）の CSV 全部
- 結果は同じフォルダに置く
- 見出しの先頭付近にある日時の列で古い順に並べ替える
- 分類も「ファイルとフォルダ」から「その他」へ移した

想定している使い方は次のとおり（あとから聞いた）。

```
日次/  ← 対象アプリが毎日 1 本ずつ吐く
    売上_20260801.csv        1  フォルダを作る        → 日次/202608
    ...                      2  ファイルをコピーする  → 31 本を入れる
    売上_20260831.csv        3  CSV をまとめる        → 月次_202608.csv
```

対象を選ばせないのは、まとめる先が「作ったフォルダ」だと決まっている以上、
そこに入っているものが対象という以外の解釈が無いため。設定項目を 1 つ
減らせるうえ、パターンを打ち間違えて 0 件になる事故も消える。

`_created_folder` を `_work_dir` と別に持っているのは、「作ったフォルダを
以降の保存先にする」を外していても、まとめる先は作った場所だから。

**出力ファイルを対象から除いている。** 除かないと 2 回目に動かしたとき
前回の結果を自分に取り込んで行が倍になる。前の実装でも起きうる問題だった。

### 日時の列は自動で見つける

「データの先頭付近にある日付」で並べる、という要件をそのまま実装した。
列名を打たせない（2 章）ので、**見出しの先頭 4 列**から探す。

1. 名前に「日時」「日付」「年月日」「date」などが入っている列を先に試す
2. 駄目なら、その列の値を実際に日時として読めるか見る（先頭 50 行の 8 割）

ファイルごとに書き方が違っても混ぜて並べられる（`2026/8/5` と `20260810` と
`2026年8月1日` が同じ列に混在していても正しく並ぶことを確認した）。
読めなかった行は**捨てずに末尾**へ回す。日時列が見つからなければ、
失敗させず読み込み順のままにして警告を出す（並んでいないだけで使えるため）。

### 時刻を落としていた（用途を聞いて直した）

最初の実装は日付だけを見ていた。`2026-08-28 10:30:00` を空白で切って
`2026-08-28` として読み、**時刻を捨てていた**。

そのあとに用途を聞いた。「1 日 1 本の CSV が貯まるので、1 か月ぶんを
フォルダに入れて 1 本の連続データにしたい。データには日時が記録されている」。

この用途では時刻を落とすと、**同じ日の中が元ファイルの並び順のまま残る**。
1 日 1 ファイルなら日ごとの順序は合うので一見動いて見えるが、1 つのファイルに
複数日が混ざったり、ファイル内が時刻順でなかった時点で崩れる。
「連続データにする」という目的からすると、静かに間違った結果を出す実装だった。

日時の書式（時刻付き 15 種）を先に試し、駄目なら日付だけの書式に落とす形に
変えた。`T` 区切り（ISO）とミリ秒も通る。**空白で切る処理は最後の保険**に
下げてある（後ろに余計な文字が付く出力のため）。

あわせて、まとまった**期間を実行ログに出す**ようにした。

```
[info]   2026-08-01 10:00:00 〜 2026-08-31 17:00:00 の 93 行
```

月 1 回・無人で動くものなので、1 か月ぶんが揃っているかをファイルを開かずに
確かめられる形が要る。日数が足りていなければここで気づける。

### 前提のある手順は、置く前に止める

「フォルダ作成工程が無ければ手順に入れられない様に」という要件。
前提を `ActionSpec.requires` として宣言側に持たせ、3 か所で効かせた。

| どこ | 何をするか |
| --- | --- |
| ［＋ 手順を追加］ | 満たしていない操作を灰色にし、理由をラベルに出す |
| 一覧・保存前の検証 | `Scenario.step_problems()` が ⚠ を付ける |
| 実行の開始時 | **対象アプリを起動する前に**止める |

メニューで止めるだけでは足りない。「種類」のドロップダウンで既存の手順を
後から「CSV をまとめる」に切り替えられるし、`--run` の無人実行は
画面を通らない。実行時の判定を `run()` の先頭に置いたのは、8 手順進んでから
「先にフォルダを作る手順が要る」と言われても遅いため。

判定を `Step.validate()` ではなく `Scenario.step_problems()` に置いたのは、
Step が自分の位置を知らないから（「**前に**あるか」を見る必要がある）。

### まだベータであることを画面に出す

「バーにヘルプや、バージョン、作成者は要らない？」という問いから。
3 つを分けて考え、**版だけ入れた**。

| | 判断 | 理由 |
| --- | --- | --- |
| バージョン | 入れる | exe を対象 PC にコピーして月 1 回動かす。1 か月後に「動いていない」となったとき、向こうに載っているのがどのビルドか分からないと調査が始まらない |
| 作成者 | 入れない | 社内の 1 人用ツールで、増える情報が無い |
| ヘルプ（メニュー） | 入れない | ファイル/編集/ヘルプ を足すとツールバーの［新規］［保存］［削除］と二重になる |

置き場所はツールバーの右端。メニューバーを新設せずに済み、
**⚠ ベータ版 0.9.0** と出しておけば「まだ作成中」が一目で分かる。
押すと用途と注意点の小窓が開く形にした。

文言は `logic/appinfo.py` に集めてある（画面と、将来ログや exe の
情報から使うときに食い違わないようにするため）。`IS_BETA` を False に
すると色と警告が消える。実機確認が済んだときの 1 行変更で済ませたい。

**実行ログと exe のプロパティにはまだ入れていない。** 無人実行の調査は
`logs/*.log` を読むので、本当はそこに版が入っているのが一番効く。
11 章の積み残しに書いた。
→ 実行ログには 6 章で入れた（古いコードが動いていた件で実際に困ったため）。
exe のプロパティはまだ。

### 保存先を実行中に動かせるようにした

`Runner._work_dir` は今まで実行中ずっと固定だった。「フォルダを作る」
「保存先フォルダを選ぶ」で差し替えられるようにし、`{work_dir}` の
差し込み変数も同時に更新している。片方だけ変えると、相対パスの解決結果と
`{work_dir}` を書いた文字列が食い違う。

確認実行では**フォルダは作らないが、切り替えだけは行う**。切り替えないと
確認実行のときだけ以降のパスが本番と違うものになり、確認の意味が消える。

### フォルダ名は打たせない

`{yyyymm}` を覚えさせない方針（2 章）をフォルダ名にも通した。
［型 ▼］に年月日の並べ方を用意し、選ぶと欄が丸ごと置き換わる。
差し込みのような「追記」にしなかったのは、フォルダ名は丸ごと決まることが
ほとんどで、継ぎ足すと打ち間違いの余地が残るため。

選んだ結果**出来上がるフルパスをその場に出す**。毎月同じフォルダに
上書きしていないかを、実行する前に目で確かめられる。

同じ考えで、コピー対象の選び方（`file_pattern`）は［型 ▼］から
「すべて」「CSV すべて」などを選ばせ、**今そこに何件あるか**を出す。
0 件のまま気づかず組んでしまうのを防ぐため。

### 消す操作は入れない

削除アクションは作らなかった。月 1 回・無人で動くものが誤って消すと、
気づくのが 1 か月後になる。

コピーの「同じ名前のとき」の既定も**飛ばす**にした。毎月動かすので
行き先に前月分が残っていても止まらず、かつ黙って消さない。上書きは
選んだときだけ（そのときだけ行き先のファイルが消える）。

### 判明したこと

`Path.glob()` は絶対パスを渡すと `NotImplementedError` を投げる
（`OSError` でも `ValueError` でもない）。ファイルの選び方の欄に
フルパスを貼られると、画面のプレビューと実行の両方で捕まえ損ねて
「想定外のエラー」になる。両方で明示的に受けている。

`tk.Menu.post()` は Windows で**そこから戻ってこない**（メニューを閉じるまで
Tk 内部のモーダルループに入る）。検証スクリプトでメニューを開いた状態を
撮ろうとしてハングした。メニューの中身は `index()` / `type()` /
`entrycget()` / `invoke()` で開かずに確かめられるので、そちらで見ること。

## 6. 起動用ファイルが exe ではなかった（2026-08-31 追加）

### 何が起きたか

「起動できないファイルが有る。固有の拡張子で、関連付けでパラメータを渡して
別の実行ファイルを起動してる？」という指摘。拡張子は `.kww` で、プロパティを
見るとショートカットに見える、とのことだった。

**起動用ファイルが exe（か bat）だと決めつけていた**のが原因。3 か所で効いていた。

| 場所 | 何が起きていたか |
| --- | --- |
| `logic/shortcuts.py` の一覧 | `rglob("*.lnk")` なので `.kww` は**そもそも一覧に出ない** |
| `ui/app_chooser.py` の直接指定 | フィルタが exe/bat/cmd。「すべて」で選べても `target` が `.kww` のまま保存される |
| `logic/runner.py` の起動 | `Application.start()` の中身は CreateProcess。**関連付けもショートカットも解決しない**ので失敗する |

### 拡張子ではなく中身で判断する

`.kww` が本当にシェルリンクかは、拡張子を変えた `.lnk` を作って実験した。
先頭 20 バイトがヘッダ長 `0x4C` ＋ `CLSID_ShellLink` なら確定する。

同じ実験で、既存の実装が読めない理由も出た。

```
.lnk: target='C:\Windows\System32\notepad.exe' args='/A "C:\temp\x.txt"'
.kww: 失敗 com_error: 『ショートカットのパス名は .lnk または .url で終わらなければなりません。』
```

`WScript.Shell.CreateShortcut` が**パスの拡張子で拒否する**。
`IShellLink` + `IPersistFile` は中身しか見ないので、同じ `.kww` を読めた。
`resolve()` をこちらに置き換えてある。

### os.startfile には逃がさない

ShellExecute に投げれば Windows が全部やってくれるが、採らなかった。
**起動したプロセスの PID が返らない**ので `Runner` が `self._app` を保持できず、
「アプリを閉じる」が窓の題名頼み（事実 #6 の結び直し）だけになる。

代わりに `logic/launch.py` を足し、Windows がダブルクリックでやっていることを
自前でたどって **exe と引数まで落としてから** `Application.start()` に渡す。
画面にも「実際に走るコマンド」を出せる。

| ファイルの中身 | たどり方 |
| --- | --- |
| exe / bat / cmd / com | そのまま |
| シェルリンク | `IShellLink` でリンク先と引数を読み、その先をもう一度たどる |
| それ以外 | レジストリの関連付けから起動コマンドを読む |

関連付けは `HKCR` だけでは足りない。「プログラムから開く」で選び直されていると
`HKCU\...\Explorer\FileExts\<拡張子>\UserChoice` が勝つ。`%1` / `%L` / `%*` の
展開も自前でやる。差し込み記号が無い書き方（DDE を使う古いアプリ）のときは
末尾にパスを足す。付けないとアプリだけ起動してファイルが開かれない。

### 実機を待たずに確かめた

対象アプリはこの PC に無いので、`.kww` の中身をこちらで作って通した。

- シェルリンクを `.kww` にコピー → `resolve()` がリンク先と引数を読めるか
- `.txt`（実在の関連付け）→ 関連付け経由で本体の exe に落ちるか
- 登録の無い拡張子 → `LaunchError` になるか
- `Runner` の `launch_app` に `.kww` を渡して dry-run と本実行
- デスクトップに `.kww` を置いて一覧に出るか

一覧の走査を `*.lnk` から全ファイル＋ヘッダ判定に変えた分のコストも測った
（0.01 秒 → 0.03 秒、239 件）。解決そのものが 2.8 秒かかるので誤差。

### 実機の結果: ショートカットではなく関連付けだった

実機で通ったのは**関連付けの経路**だった。プロパティがショートカットに
見えたのは、`.kww` が `IsShortcut` 付きで登録されているためで、
中身はシェルリンクではなかった。

```
"C:\Program Files\Panasonic-EW Control\KW Watcher\KW Watcher.exe" "C:\Users\...\ガス.kww"
```

**両方の経路を作っておいたのが効いた。** 実機が手元に無い状態で
「たぶんショートカット」の 1 本だけ作っていたら、対象 PC に持ち込んで
初めて外れが分かり、往復がもう 1 回増えていた。実機で確かめられない
ときは、分かれ道を潰さずに両方通しておくほうが速い。

### 引用符を二重にしていた

実機で出た起動コマンドに、こちらのバグが写っていた。

```
"...\KW Watcher.exe" ""C:\Users\R010473\Desktop\ガス.kww""
                     ↑↑                              ↑↑
```

レジストリの雛形が `"%1"` と**すでに引用符で囲まれている**のに、
`%1` を引用符付きのパスで置き換えていた。

**今回は偶然動いた。** パスに空白が無いと、Windows の引数解析が
`""C:\...\ガス.kww""` を 1 つの引数として通してしまう。空白があると割れる。

```
"C:\Program Files\My Data\ガス 1 月.kww"     → ["C:\Program Files\My Data\ガス 1 月.kww"]
""C:\Program Files\My Data\ガス 1 月.kww""   → ["C:\Program", "Files\My", "Data\ガス", "1", "月.kww"]
```

囲み済みかどうかを見て二重にしないようにした（`expand_args()`）。
**動いたから正しい、とは限らない**種類の不具合で、実機のパスが
`Desktop` 直下だったから表面化しなかっただけ。

### どのコードが動いているか分からなかった（版をログに出した）

対象 PC で試してもらったら、**まったく同じエラーが 2 度出た**。

```
起動に失敗しました: Could not create the process ""C:\Users\R010473\Desktop\ガス.kww""
Error returned by CreateProcess: (193, 'CreateProcess', '%1 は有効な Win32 アプリケーションではありません。')
```

CreateProcess の 193 は「実行ファイルではない」なので診断自体は裏付けられたが、
**この文言は変更後のコードでは出せない**（`.kww` が `Application.start()` まで
届かない）。つまり対象 PC 側が古いままだった、ということまでは分かる。
分からないのは「では今どれが動いているのか」で、**ログを見ても答えられない**。

11 章の積み残しにあった「実行ログの先頭に版を出す」を、ここで入れた。

```
Win RPA 0.9.1（ベータ版）
実行を開始します（1 手順）
```

無人実行の失敗は `logs/*.log` を読んで調べる前提なので、そこに版が無いと
今回と同じ「更新したはずのコードで話をしている」状態が毎回起きる。
文言は `logic/appinfo.py` の `log_line()` に置いた（画面の表示と同じ場所）。

### 選んだ直後の一覧が嘘をついていた

同じ画面写真に、**フォームは「ガス」なのに一覧は「1. (未指定) を起動する ⚠」**
という状態が写っていた。

`choose_app` / `pick_element` は選び終わったあと `_refresh_steps()` を呼んで
一覧を組み直していたが、**`collect()` を通していなかった**。入力値は
エディタの中にあるだけで `Step.params` にはまだ無いので、組み直しても
古い内容が描き直されるだけだった。`_commit_and_refresh()` にまとめてある。

実害は無い（保存や実行の前に `collect()` が走る）が、⚠ が出たままなので
**指定できていないように見える**。今回のように別の不具合を追っているとき、
これが混ざると切り分けが増える。

### 古かったのは exe だった（そして exe でだけ落ちた）

「ビルドの方の py は更新していない？」と聞かれた。**ビルド用の別コピーは無い**
（`tools/build.py` は `apps/win_rpa/main.py` を直接ビルドする）。単に
`build/dist/win_rpa/win_rpa.exe` が 3 日前のままだった。

作り直して、exe の無人実行（`--run`）で確かめたところ**別の不具合が 2 つ**出た。
どちらも Python 実行では再現せず、**exe でしか出ない**。

**1. `win32timezone` の同梱漏れ**

```
File "logic\shortcuts.py", line 147, in resolve
ModuleNotFoundError: No module named 'win32timezone'
```

pywin32 が COM の日時（FILETIME）変換で**遅延 import** しているため、
import 文としてコードに現れず PyInstaller の解析に出ない。
`tools/build.py` に `_HIDDEN_IMPORTS` を足した（アプリごとに指定する）。

**2. `ShortcutError` が実行全体を落としていた**

`resolve_launch()` が `shortcuts.resolve()` の例外をそのまま外へ流していた。
`Runner` は `AutomationError` しか手順の失敗として扱わないので、抜けると
**手順の失敗ではなくプロセスごと落ちる**（`--windowed` なので
「Unhandled exception in script」のダイアログが出て固まる）。
`LaunchError` に包み直した。

無人実行の途中でこれが起きると、**ダイアログが出たまま誰も見ていない**状態に
なる。月 1 回のスケジュール実行では最悪の落ち方なので、`logic/` から
`AutomationError` 以外を投げないことは今後も守る。

### exe の確認のやり方

`--run` はログをファイルに残すので、**画面を見なくても中身が新しいか確かめられる**。

```
12:53:09 [info] Win RPA 0.9.1（ベータ版）             ← 版が出る
12:53:09 [step] 手順 1: ガス を起動する
12:53:09 [ok]   … 起動できる状態です（ショートカット → notepad.exe）
```

`--windowed` の exe は例外がダイアログに出て固まるので、`subprocess` で
起動して **stderr をファイルに落として殺す**形にした。トレースバックは
パイプに出ているので、ダイアログを閉じなくても読める。

## 7. 名前のないボタンが選べなかった（2026-08-31 追加）

### 何が起きたか

実機（KW Watcher）で「アプリケーションの表示変更タブボタンに、名前の無い
ボタンとしてボタン選択できない物が有ります」という指摘。

**ピッカーが記録を拒否していた。** 実行側は照合の 3 段目（構造上の位置）で
探せるのに、記録する側の `is_identifiable()` が名前も AutomationId も無い
要素を弾いていた。作った側の非対称で、能力はあるのに入口で止めていた。

もとの意図は 2 章の「Tkinter 製アプリを早く判別する」だった。**アプリ全体が
無名なのか、一部のボタンだけが無名なのかを区別していなかった**のが間違い。

### 位置に落ちる前に、名前を 2 通り増やした

いきなり位置で妥協するのではなく、先に取れるものを増やした。
アイコンだけのボタンでも、この 2 つは入っていることが多い。

- **ツールチップ**（UIA の `HelpText`）
- **古い形式の名前**（`LegacyIAccessible` の `Name`。Win32 / MFC のツールバー）

照合は AutomationId → 名前 → ツールチップ → 古い形式の名前 → 位置 の 5 段に
なった。3・4 は `child_window()` の条件に指定できないので、その段に落ちた
ときだけ `descendants()` を自分で見て回る（1・2 が当たれば走査しない）。

メモ帳のボタンで、名前を落とした `ElementRef` を作って確かめた。

```
そのまま（名前あり）                  → 見つかる
名前を落とす（古い形式の名前だけ）    → 見つかる
名前も古い形式も落とす（位置だけ）    → 見つかる ＋ 警告が出る
```

### 位置だけの要素は、記録する前に確認する

拒否をやめたが、黙って通しもしない。位置しか無い要素は
`messagebox.askyesno` で「ボタンが増減すると隣を操作する」ことを
示してから記録する。実行時も `MATCH_PATH` で見つけたら毎回警告を出す。

**警告を毎回出すのは、無人実行だと誰も見ていないから。** 月 1 回動くものが
静かに隣のボタンを押していた場合、気づくのは 1 か月後になる。ログに
残っていれば、結果がおかしいと分かった時点で照合の段まで遡れる。

### 一覧で見分けが付くようにした

「名前の無いボタン」が並ぶと、手順一覧で全部同じ表示になる。
`describe()` に**同種の中で何番目か**を出すようにした。

```
ボタン「更新」              名前がある
ボタン（btnRefresh）        AutomationId がある
ボタン〔表示を切り替える〕   ツールチップ／古い形式の名前がある
名前のないボタン（3 個目）   位置だけ
```

### 保存形式を増やしたので、往復を確かめた

`ElementRef` に項目を 2 つ足した。`from_dict()` が **知らないキーを捨てる**
ようにしてある。項目を増やす前に保存されたシナリオと、逆に新しい項目を
持つシナリオを古いコードで開いた場合の両方で落ちないため。

## 8. 実行ボタンの整理（2026-08-31 追加）

### 求められたこと

「ここまで試し実行の左に、選択された手順のみの実行が欲しい」
「最初から確認実行と実行の違いが分からない」。

### 名前が悪かった

後者は機能ではなく**名前の問題**だった。

| もとの名前 | 実際にすること |
| --- | --- |
| ここまで**試し**実行 | **操作する**。最初から選んだ手順まで |
| 最初から**確認**実行 | **操作しない**。対象が見つかるかだけ |
| 実行 | 操作する。全部 |

「試し」と「確認」は日本語として近いのに、**片方は操作し、片方はしない**。
一番大きな違いがいちばん読み取りにくい名前になっていた。

「操作するかどうか」を名前に出す形に変えた。

```
［動かさず確認］ ｜ ［この手順だけ動かす］ ［ここまで動かす］ ［最初から動かす］
```

操作しないものだけを区切りの左に置き、右の 3 つは**範囲が広がる順**に並べた。
下に 1 行の説明も出している。名前を変えただけでは、既にどちらかを
使っている人が「変わった」ことに気づけないため。

### 手順 1 つだけの実行

`Runner.run()` に `only` を足した。`upto` と同じく、
**実行エンジンの中身は変えていない**（動かす手順の並びを作る箇所だけ）。

1 つだけ動かすときの決めごとは 2 つ。

- **前の手順は動かさない。** 対象アプリは自分で開いておく。要素は記録された
  ウィンドウ題名から探すので、起動済みなら見つかる（`_window_for` が
  デスクトップ全体を見るため）
- **未入力の検証も、その手順しか見ない。** 組み立て途中で他の手順が
  埋まっていないのは当たり前で、そこで止めると「直した 1 つを試す」
  という用途そのものが成り立たない

前提条件（「先にフォルダを作る手順が要る」）の判定だけは、
**シナリオ上その手前にある手順**を使う。実際には動かさないが、これは
シナリオの形の話なので、1 つだけ動かすときも基準を変えない。

## 9. RPA として基本の操作を足した（2026-08-31 追加）

### 求められたこと

「手順内容として RPA に基本必要だろうと思われる作業種類を追加して」。

### 何が足りていなかったか

それまでの操作は「要素を 1 つ選んで、押す・入れる」に寄っていた。
業務アプリを触るとき、それだけでは届かない場所がある。

| 足りなかったもの | 足したもの |
| --- | --- |
| ボタンになっていない操作（Enter で確定、Tab で次の欄、Ctrl+S） | キーを押す |
| 開かないと存在しないメニュー項目 | メニューから選ぶ |
| 別ウィンドウを開くアプリで、操作対象を移す | ウィンドウを前面に出す |
| 「よろしいですか？」の確認 | メッセージに応じる |
| 入力ファイルを読み込ませる（保存の対） | 「ファイルを開く」に応じる |
| 一覧の項目を開く／右クリックメニューを出す | ボタンを押す に［押し方］ |
| 合図で待てない処理 | しばらく待つ |
| バッチや別ツールの呼び出し | 別のプログラムを実行する |
| 成功した経過の証跡 | 画面を保存する |

宣言（`ACTIONS`）に足して `Runner` に処理を書くだけで済み、`ui/` は
`keys`（キーを一覧から選ぶ欄）を 1 つ増やしただけだった。分類・前提・
フォーム生成を宣言側に寄せた形が、増やすときに効いた。

### キーの書き方はユーザーに見せない

`{ENTER}` や `^s` は pywinauto の書き方であって、業務の言葉ではない。
`KEY_CHOICES` に「Enter（決定）」「Ctrl+S（保存）」の形で並べ、
画面には説明を出し、保存されるのは pywinauto に渡す値のほうにした。
フォルダ名の［型 ▼］と同じ考え方。

### メニューは要素の照合では見つからない

開いたメニューは、アプリの画面とは**別の最上位ウィンドウ**として出る。
`_resolve`（記録した識別子で探す経路）は「要素が属するウィンドウ」を
起点にするので、ここには届かない。ウィンドウを列挙して `MenuItem` を
名前で探す別経路にした。

最初は起動したプロセスだけを見ていて、メモ帳で試したら
`app.windows()` が空だった。**メモ帳がランチャー型**で、
`Application.start()` が返すプロセスがウィンドウを 1 つも持たない。
6 章と同じ形の問題に、別の場所でもう一度当たったことになる。

起動したプロセスがウィンドウを持たないときに限り、いま手前にある
ウィンドウのプロセスへ広げる形にした。デスクトップ全体を走査する手も
あるが、それは画面上のすべてのアプリの UI ツリーをたどることになり、
待ち時間の判定より先に終わらなくなる。**探す範囲は必ずプロセス単位に絞る。**

はじめは条件を付けずに前面のウィンドウを足していたら、アプリを起動して
いない状態の検証で**開発中の VS Code のメニューを開いてしまった**。
無人実行で対象アプリの起動に失敗したら、同じことが本番で起きる。
アプリを掴んでいることを条件にし、掴んでいなければその場で止めるようにした。

### 失敗時の画面が 1 枚も残っていなかった

「画面を保存する」を書いていて、失敗時の記録が
`Desktop(backend="uia").capture_as_image()` を呼んでいることに気づいた。
`capture_as_image` は**ウィンドウ 1 つ分**を撮るメソッドで `Desktop` には無く、
`except Exception: return None` に吸われて毎回黙って諦めていた。

PIL の `ImageGrab.grab(all_screens=True)` に置き換え、両方から使う
`_capture_screen()` に集約した。ダイアログが別モニタに出ても写る。

握りつぶす `except` の範囲を「記録が失敗しても実行は続ける」ために
広く取ると、こういう**そもそも動いていない**が見えなくなる。
`OSError` だけ受けるように狭めた。

### 確かめたこと

対象の業務アプリは今も無いので、メモ帳を相手に実機で通した。

- 起動 → キーを送る（Enter ×2）→ メニュー「編集 > すべて選択」→ Esc
- 起動 → Ctrl+O → 「ファイルを開く」に応じる → 画面を保存する
  （画像に読み込んだ内容が写っていることまで確認）
- メッセージに応じる … 出ていないとき飛ばす／失敗にする の両方
- ウィンドウを前面に出す … 自分で出した Tk の窓を対象に
- 全 22 種類の編集フォームが例外なく組み上がること、
  宣言にあって `Runner` に処理が無い操作が 1 つも無いこと

## 11. 検証のやり方

CLAUDE.md の方針どおり、検証スクリプトはリポジトリに置かず一時フォルダに書いて捨てている。
書き直すときの中身を残しておく。共通の下ごしらえは次の 2 つ。

- `sys.path.insert(0, "apps/win_rpa")` してから `logic` / `ui` を import する
- `messagebox` を差し替えて、ダイアログでスクリプトが止まらないようにする

```python
import ui.main_window as mw
errors: list[str] = []
mw.messagebox.showerror = lambda t, m, **k: errors.append(f"{t}: {m}")
mw.messagebox.askyesno = lambda t, m, **k: True
```

| 検証 | 内容 |
| --- | --- |
| ピッカー | ダミーを起動し、各ウィジェットの座標から `capture_at()`。`auto_id` / 種類 / 推定操作 / JSON 往復を確認 |
| 通し実行 | 採取した要素で `Scenario` を組み、`Runner` で dry-run と本実行。2 か月分まわして結合まで |
| 無人実行 | `subprocess` で `main.py --run <名前>` を叩き、CSV とログファイルを確認。存在しない名前で終了コード 2 |
| UI | `root.update()` を回し、全アクションのフォーム項目・完了条件の切り替え・並べ替えを確認 |
| グループ | `Treeview` の iid（`g<番号>` / `s<位置>`）を直接 `selection_set` して各操作を叩き、`Step.group` の並びを見る |
| ファイル操作 | 一時フォルダに CSV を置き、`Runner` を通してから実際に出来たファイルを数える |
| まとめる | 日時の書き方を混ぜた CSV を 3 本置き、まとめた結果の列を読んで**並び順そのもの**を確かめる。2 回続けて動かして行が倍にならないことも見る |
| 1 か月ぶん | **実際の使い方どおりに組む。** 1 日 3 行 × 31 日の日次ファイルを作り（各日は時刻をわざとばらす）、フォルダ作成 → コピー → まとめを通して、結果が時刻まで単調に並ぶことと前月分が混ざらないことを見る |

| シナリオ管理 | 3 本作って切り替え、未保存時の引き止め、名前衝突 |

## 13. 配布フォルダを削った（2026-08-31 追加）

### 求められたこと

「ビルドフォルダの win_rpa 内に多くのファイルとフォルダが有るが、全て実行に
必要な物？ 実行 PC にコピーするのも時間がかかる」。

### 全部は要らなかった

**64.1 MB / 989 ファイル**のうち、半分以上が一度も通らない経路のものだった。
PyInstaller は「import 文がある」だけで丸ごと拾うため。

| 外したもの | 大きさ | 誰が引っぱっていたか |
| --- | --- | --- |
| `numpy` | 26.7 MB | `comtypes._npsupport`。COM の SAFEARRAY を ndarray で受け渡すための連携で、`enable_numpy_interop()` を呼んだときだけ動く。pywinauto は呼ばない |
| `PIL.AvifImagePlugin` | 7.5 MB | `PIL.Image` が起動時に全プラグインを試すため。保存するのは PNG だけ |

`tools/build.py` に `_EXCLUDES` を足して `--exclude-module` を渡す形にした。
`_HIDDEN_IMPORTS`（足りないものを足す）と対になる。

結果は **28.1 MB / 963 ファイル**。大きさは 56 % 減った。

### 「無駄に見えるが外せないもの」があった

`pythonwin`（`win32ui.pyd`、1.1 MB）も外そうとしたが、xref を読んだら
`pywinauto.base_wrapper` が**先頭で `import win32ui` している**。
外していたら exe が起動時に落ちていた。

`libcrypto` / `libssl`（4.0 MB）は `ssl` が引いている。このアプリは通信を
しないので外せるはずだが、`urllib` 経由で踏む経路が残っていないか
確かめきれなかったので触っていない。4 MB のために月 1 回の無人実行を
賭ける取引ではない。

### コピーが遅い原因は大きさではなかった

削っても **963 ファイル**残る。**うち 830 は tcl のスクリプト**（`_tcl_data`、
たった 3.2 MB）で、Tkinter を使う限り消せない。小さいファイルを大量に
コピーするのは、同じ容量を 1 ファイルで渡すより桁で遅い。

つまり削るだけでは解決しない。**zip にして 1 ファイルで渡す**のが答えで、
圧縮すると 12.6 MB になる。

### `--onefile` は採らなかった

1 ファイルの exe も作って測ったら 12.7 MB で、zip とほぼ同じだった。
これなら配布形態として楽なので試したところ、**起動のしかたで結果が変わった**。

| 起動のしかた | 結果 |
| --- | --- |
| エクスプローラーからダブルクリック | 動く |
| `Start-Process` | 動く |
| PowerShell の `&` | `Security validation failure: parent process has different executable!` のダイアログが出て止まる |
| Python の `subprocess` | 同上。無人実行が 412 秒待っても終わらず、終了コード -1 |

PyInstaller 6 系のブートローダーが、展開後の子プロセスで「親プロセスの
実行ファイルが自分と同じか」を検証している。コンソールを持つプロセスから
起動したときにこれが誤検知する。

**画面が出ない `--windowed` でこれが起きるのが特に悪い。** ダイアログは
出ているが誰も見ておらず、プロセスは終わらないまま残る。月 1 回の
スケジュール実行で起きたら、気づくのは翌月になる。

`--onedir` ＋ zip なら同じ 12〜13 MB でこの危険が無いので、そちらにした。
5 章までの「`--onefile` にはしない」という判断は、理由は違うが結論として
正しかったことになる。

### 確かめたこと

削った exe（`--onedir`）で、

- 無人実行（`--run`）が終了コード 0 で通り、ログが出る
- 「画面を保存する」で PNG が実際に作られる（PIL を削った影響が無い）
- 画面を出して起動し、1.0 秒でウィンドウが現れる

## 14. 用途の説明が狭かった（2026-08-31 追加）

### 指摘

「月一のルーティンワークに限らず、シナリオ選択で一ルーティーンを実行できる
事も説明」。

### 機能ではなく説明の問題

**選んで動かす機能は最初からあった。** 画面の左上にシナリオの一覧があり、
選んで［最初から動かす］を押せばその 1 本が走る。`--run <シナリオ名>` も
スケジューラ専用ではなく、ただの「画面を出さずに 1 本動かす」入口。

にもかかわらず、説明が全部「月 1 回」から始まっていた。

| 場所 | 直す前 |
| --- | --- |
| README の 1 行目 | 「月 1 回のルーティンワークを、スケジュール実行で無人化することを目標にする」 |
| 「について」の小窓 | 「月に 1 回のルーティンワークを、人が張り付かずに…」 |
| 使う流れの最後 | 「［保存］→［スケジュール...］で毎月の実行日時を登録する」 |

**手順の最後がスケジュール登録になっていたのが特に悪い。** 登録しないと
完成しないように読める。実際には保存した時点で動かせる。

### 直したこと

- 保存とスケジュール登録を**別の段**に分けた。7 で「ここまでで、いつでも
  動かせる状態」と言い切り、8 を「毎月任せたいときだけ」にした
- 「そのとき 1 本だけ動かす」を README と「について」の両方に足した
- スケジュールは**シナリオの属性ではない**ことを設計方針に明記した。
  タスクスケジューラ側に別に登録するもので、シナリオ自体は
  「選んで動かせる作業のまとまり」でしかない。月次に縛られない作りは
  この分離から来ている
- シナリオ 1 本を指すショートカットの作り方を書いた。
  `make_shortcut.py --args "--run 売上集計"` で、ダブルクリックすると
  そのシナリオだけが走る（画面なし、結果は `logs/`）。
  **書く前に実際に作って動かし、ログが出るところまで確かめた**

### 分かったこと

出来ることが増えたときは、機能を足すだけでなく**最初の 1 行を読み直す**。
「何のためのソフトか」は最初に書いた用途のまま固まりやすく、後から広がった
使い方は、作った本人以外には見えない。

## 15. コピー対象を更新日で絞る（2026-08-31 追加）

### 求められたこと

「ファイルコピーの対象ファイルを更新日範囲で選択できるようにしたい」
「先月とか」。

### 名前で絞る手は既にあったが、届かない

`対象のファイル` の［型 ▼］には `*{prev_yyyymm}*.csv`（名前に 202607 を含む）が
入っていて、**ファイル名に日付が入っている出力**なら前月分だけを拾えた。
しかし業務アプリの出力が `売上.csv` のような固定名だと、この手は使えない。
そこで**ファイルの更新日時**で絞る口を足した。

### 日付は打たせない

「先月とか」という言い方がそのまま答えで、欲しいのは日付欄ではなく
**月次で使う言い方の一覧**だった。`DATE_RANGES` に

    指定なし / 先月（1 日〜末日）/ 今月（1 日〜今日）/ 今日 / 昨日 /
    直近 7 日 / 直近 30 日 / 期間を指定する

を並べ、選ぶと**今日動かすといつからいつまでになるか**を欄の下に出す。
「先月」を選んで 7 月になっているかを、その場で確かめられる。
フォルダ名の［型 ▼］と同じ考え方（[[ui-prefers-selection-over-typing]]）。

決まった期間を指定したい場合だけ、年・月・日をスピンボックスで選ばせる。
ここも打ち込みではない。2 月 31 日のような組み合わせは `clamp_day()` が
末日に丸める（エラーにすると「月末まで」を選びたい人が困る）。

### 「今日」は実行の最初に 1 度だけ決める

`Runner` が `self._today` を持つようにした。差し込み変数（`{yyyymm}`）と
更新日の絞り込みが**同じ日**を見る必要があるため。日付をまたいで動くと、
先月ぶんを集めているのに保存先だけ翌月、ということが起きる。

### 0 件になったときに、原因が分かるようにする

絞り込みを足すと「0 件でした」の意味が 2 通りになる。**対象アプリが
出力に失敗した**のか、**範囲の選び間違い**なのか。月 1 回しか動かさないので、
ここが読めないと調査が翌月まで持ち越しになる。

そこで実行ログに「`*.csv` は 6 件。そのうち更新日が 先月 のものは 3 件です」と
両方の数を出し、`最低件数` を下回ったときのエラーにも**絞る前の件数と
選んでいる範囲**を載せた。

### 別の親に grid した部品は描かれない

期間指定の日付欄が**画面に出なかった**。場所だけ空いていて中身が無い。

原因は、部品を `_DayPicker(self, ...)`（＝ `DateRangeEditor` の子）として作り、
表示だけ `grid(in_=self._custom)` で入れ物に入れていたこと。Tk は
`in_` で別の入れ物に配置できるが、**重なり順は親子関係のまま**なので
入れ物の下に隠れる。入れ物を先に作り、その子として部品を作れば直る。

**画像で見なければ気づけなかった。** `winfo_exists()` も値の保存・復元も
通っていて、自動確認はすべて緑だった。画面を組む変更は、`ImageGrab` で
1 枚撮って目で見る。

### 確かめたこと

- 型ごとの範囲を固定日で検算（年またぎ・うるう年・逆順の入れ替えを含む）
- 更新日をずらした 6 ファイルを実際に作り、「先月」で 3 件だけが運ばれること
- 範囲に 1 件も無いときに、絞る前の件数を添えて失敗すること
- 確認実行の表示、選んだ内容の保存・復元、フォームの見た目（画像）
