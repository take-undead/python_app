# win_rpa 開発の経緯

このアプリを作るまでに決めたこと、途中で判明したこと、まだ終わっていないこと。
仕様と使い方は [README.md](README.md) を見ること。ここは「なぜそうなっているか」と
「今どこにいるか」を残すためのもの。

作成: 2026-08-27 〜 2026-08-28

---

## 1. 何を作ろうとしているか

月 1 回の PC ルーティンワークの自動化。具体的には次の流れ。

1. Windows の業務アプリを起動する
2. 決まった順にボタンを押し、値を入力する
3. アプリに CSV を出力させる
4. 出力された複数の CSV を 1 つに結合する

これをスケジュール実行で無人化することが最終目標。

**対象の業務アプリは開発機（この PC）に入っていない。** そのため、
実機なしで最後まで作れるように練習用のダミーアプリを用意してある。

## 2. 設計で決めたこと

### 記録するのは座標ではなく「要素の同一性」

最初に検討したのはマクロレコーダー方式（マウス座標とキー入力を時系列で記録）
だが、これは採らなかった。ウィンドウ位置が数 px ずれただけで全滅し、
記録された内容を人が読んでも意図が復元できない。月 1 回しか動かさないアプリで
これをやると毎月デバッグすることになる。

代わりに、クリック対象の **AutomationId / 名前 / 種類 / 構造上の位置** を採取して
残し、実行時はそれで要素を探す。照合は 3 段構えで、前段が外れたら次に落ちる。
どの段で見つけたかは実行ログに残す。

### アクションの追加コストを 10 行に抑える

「出来ることが増えると UI が膨らむのでは」という懸念に対する答え。
アクションごとに専用フォームを書くと種類数 × 60 行で増えるが、
入力項目を `logic/actions.py` の `ACTIONS` にデータとして宣言し、
`ui/field_editors.py` が `kind` を見てウィジェットを選ぶ形にした。

結果、アクションを 1 つ増やすコストは宣言 10 行と `runner.py` のハンドラのみ。
**`ui/` は触らない。**

### 制御構造を入れない

`if` / `while` / 変数を入れると手順一覧が入れ子のツリーになり、条件式を書く UI と
デバッグ機能が要る。これはプログラミング言語を作る作業で、規模が桁で変わる。
月次ルーティンは平坦な直線で書けるはずなので、そこは死守する。

特殊処理が必要になったときの逃げ道として `run_python` アクションを 1 つだけ用意した。
用意したスクリプトを呼ぶだけで、ユーザーから見れば普通の操作の 1 つに見える。

### JSON をユーザーに見せない

「JSON が分からないので選択で指定したい」という要望から、方針を変更した。
JSON は内部の保存形式に徹し、画面には一切出さない。
要素はピッカー、アプリはショートカット一覧、ウィンドウ題名は開いている
ウィンドウの一覧、差し込み変数は「差し込み ▼」メニューから選ぶ。

自由入力が残っているのは、入力値そのもの（対象アプリに打ち込む文字列）だけ。

### 全自動レコーダーは作らない

バックグラウンドで全操作をフックする方式は、実装量が跳ね上がる割に余計な
クリックまで拾って結局手で削ることになる。半自動のピッカー
（マウスを乗せて F8）にして、**手順の骨格は人が組み、識別子の採取だけ機械にやらせる**
分担にした。要素の種類から操作も自動推定する（Button → 押す、Edit → 文字入力）。

### スケジューラを自作しない

月 1 回のために常駐プロセスを持たない。Windows タスクスケジューラに
`schtasks` で登録する。PC 再起動やログオン後の復帰は OS に任せる。

## 3. 途中で判明した技術的な事実

詳細は [README.md](README.md) の「分かっていること」に書いた。ここでは
どういう順で分かったかを残す。

| # | 事実 | どう表面化したか |
| --- | --- | --- |
| 1 | Tkinter のウィジェットは UIA から見えない | 雛形アプリを UIA で覗いたら名前のない `Pane` の入れ子だった。**ダミーアプリを WinForms で作り直す判断につながった** |
| 2 | PowerShell 5.1 は BOM なし UTF-8 の .ps1 を ANSI で読む | ダミーアプリが構文エラーで起動しなかった。`-EncodedCommand` で回避 |
| 3 | WinForms の `class_name` は実行ごとに変わるハッシュを含む | 照合に使わない設計にした |
| 4 | OneDrive 環境でデスクトップの実体が移動する | この開発機がその状態だった |
| 5 | `Application.start()` の `WaitForInputIdle` はコンソール起動の exe で落ちる | ランチャー型アプリで再現。`wait_for_idle=False` に |
| 6 | 起動用 exe と画面を持つプロセスが別なことがある | `close_app` がランチャーだけ殺していた。PID の結び直しを追加 |
| 7 | 共通ダイアログ（`#32770`）は UIA の走査から漏れる | 保存ダイアログが 30 秒待っても見つからなかった。Win32 では `visible=True` で存在していた。`logic/winfind.py` を追加 |
| 8 | 共通ダイアログのボタン名は日本語 Windows でも `Save` / `Cancel` | 「保存」で探して見つからなかった。`auto_id`（IDOK=1）で照合 |
| 9 | ファイル名欄への UIA `SetValue` は COM エラーで失敗する | 入力方法を 5 通り比較し、win32 の `WM_SETTEXT` だけが成功 |
| 10 | ファイル名欄の `control_id` は Windows 11 で 1001 | よく知られた 1148 は UIA 側に要素すら無かった |
| 11 | `schtasks` の出力は UTF-8（cp932 ではない） | 登録は成功するのに一覧に出なかった。タスク名が化けていた |
| 12 | Tk のウィジェットに `_register` という名前を付けると壊れる | スケジュール画面が生成された瞬間に落ちて何も表示されなかった |

7〜10 は保存ダイアログ 1 つを動かすために全部必要だった。**業務アプリは
この共通ダイアログを多用するので、ここが通らないと実用にならない。**

## 4. ユーザーからの指摘で直したこと

作ったあとで使ってもらい、次を直した。いずれも「自分では気づけなかった」類の指摘。

| 指摘 | 実際に起きていたこと |
| --- | --- |
| ウィンドウ題名が手入力なのが不便 | 自由入力が 1 か所だけ残っていた。開いているウィンドウの一覧から選ぶ形に変更（UWP の隠しウィンドウは `DWMWA_CLOAKED` で除外） |
| シナリオは 1 つしか持てないのか | 複数持てるが、切り替えで未保存の編集が黙って消える／同名で上書きされる／使えない文字を含む別名が同じファイルになる、の 3 つのバグがあった |
| スケジュール画面に何も表示されない | 事実 #12 と #11。画面がそもそも開けていなかった |
| スケジュールの一覧表示と削除は不要か | 必要だった。**シナリオを削除してもタスクが残り、毎月起動しては失敗し続ける状態**だった |
| ［＋ 手順を追加］が見つけにくい | `ttk.Menubutton` は Windows のテーマで枠が描かれずラベルに見える。一覧の右上に移し、`ttk.Button` ＋ 専用スタイルに変更 |

## 5. 今どこまで来ているか

### 動作を確認したもの

すべてダミーアプリ（`tools/mock_target.py`）相手。

- **通し実行** — 起動 → 年月入力 → 区分選択 → チェック → 集計 → CSV 出力 →
  保存ダイアログ → 行数検証 → 終了 → 結合（2 件 → 291 行）
- **確認実行（dry-run）** — 9 手順すべて、操作せず要素の存在だけ確認
- **途中まで実行（`upto`）** — 指定した手順で停止
- **無人実行（`--run`）** — スケジューラから呼ばれる経路。ログがファイルに残る。
  差し込み変数 `{prev_yyyy-mm}` が前月に展開されることも確認
- **UI** — 11 アクションすべてが正しい項目でフォームを組む。完了条件の動的切り替え、
  種類変更時の項目引き継ぎ、未入力での実行阻止、並べ替え・複製・削除
- **ダイアログ 3 種** — スケジュール／アプリ選択／要素ピッカーの生成
- **シナリオ管理** — 複数保存・切り替え・未保存時の引き止め・名前衝突の検出
- **スケジュール** — 登録・一覧・個別削除・シナリオ削除／改名への追従
- **ショートカット起動** — `os.startfile` で `.lnk` から起動し、閉じて残らないこと

### まだ確認していないもの

1. **実機（対象の業務アプリ）での動作**  
   最初にやること。`apps/win_rpa/` を対象 PC にコピーし、
   `python apps/win_rpa/pick.py` を動かして、業務アプリのボタンが
   UIA から見えるかを確かめる。名前も AutomationId も出ない場合は警告が出る。
   **ここが駄目なら座標・画像マッチに落ちるので設計から変わる。**

2. **登録したタスクが実際に時刻どおり発火するか**  
   登録・一覧・解除は確認済みだが、日付をまたぐ検証はしていない。

3. **exe 化**  
   `logic/storage.py` は `sys.frozen` で分岐済みだが未検証。
   `python tools/build.py win_rpa --onedir` で作ること
   （`pywinauto` / `comtypes` は同梱漏れが出やすいので `--onefile` にしない）。

## 6. 検証のやり方

CLAUDE.md の方針どおり、検証スクリプトはリポジトリに置かず一時フォルダに書いて捨てている。
書き直すときの中身を残しておく。共通の下ごしらえは次の 2 つ。

- `sys.path.insert(0, "apps/win_rpa")` してから `logic` / `ui` を import する
- `messagebox` を差し替えて、ダイアログでスクリプトが止まらないようにする

```python
import ui.main_window as mw
errors: list[str] = []
mw.messagebox.showerror = lambda t, m, **k: errors.append(f"{t}: {m}")
mw.messagebox.askyesno = lambda t, m, **k: True
```

| 検証 | 内容 |
| --- | --- |
| ピッカー | ダミーを起動し、各ウィジェットの座標から `capture_at()`。`auto_id` / 種類 / 推定操作 / JSON 往復を確認 |
| 通し実行 | 採取した要素で `Scenario` を組み、`Runner` で dry-run と本実行。2 か月分まわして結合まで |
| 無人実行 | `subprocess` で `main.py --run <名前>` を叩き、CSV とログファイルを確認。存在しない名前で終了コード 2 |
| UI | `root.update()` を回し、全アクションのフォーム項目・完了条件の切り替え・並べ替えを確認 |
| ダイアログ | 3 つの `Toplevel` を 1 回ずつ生成し `winfo_exists()` を見る。**生成時に落ちるバグがあったので必須** |
| シナリオ管理 | 3 本作って切り替え、未保存時の引き止め、名前衝突 |
| スケジュール | 実際に `schtasks` へ登録 → 一覧 → 個別削除 → シナリオ削除で追従。**後始末を必ず入れる** |

### 注意

- 失敗するとダミーアプリのウィンドウが残る。開始時と各実行後に
  `MainWindowTitle` が空でない `powershell` プロセスを落とすこと。
  残ったまま次を動かすと `ElementAmbiguousError` になる。
- PowerShell から Python を叩くとき `2>$null` を付けない。
  Windows PowerShell 5.1 はネイティブコマンドの stderr をリダイレクトすると
  終了コードを壊し、成功しているのに失敗に見える。
- Tkinter の画面確認は `Desktop(backend="win32")` で `capture_as_image()` すると
  画像で確かめられる（UIA では中身が見えないため）。

## 7. 積み残しの改善案

急ぎではないが、使っていて不便なら。

- **手順のコピーを別シナリオへ** — 似た手順を作るときに毎回組み直している
- **実行ログを画面から開く** — 今は `logs/` を手で開く必要がある
- **失敗した手順から再開** — 途中で落ちたとき、最初からやり直している
- **要素の再取得** — アプリ更新で見つからなくなった要素を、エラー画面から直接
  選び直せるようにする（今は手順を選び直して［要素を選ぶ...］を押す）
